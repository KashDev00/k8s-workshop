# Step 02: HAProxy Load Balancer Setup

**Playbook Reference:** `ansible/playbook_lb.yaml`  
**Target Node:** Dedicated Load Balancer VM (`loadbalancer`)

In this architecture, OpenStack Amphora/Octavia provides the Load Balancer VIP for the Kubernetes API (`port 6443`), while a dedicated **HAProxy VM** serves as the ingress entrypoint for application HTTP traffic (`port 80`), forwarding requests to the worker nodes on NodePort `30080`.

Execute the following steps **only on the `loadbalancer` VM**.

---

## 🔌 Before You Begin: Finding IPs & Connecting via SSH

1. **Find your Load Balancer & Worker IP addresses:** Check your Ansible inventory file from the project root to get the IP address of `loadbalancer` and your 3 worker nodes (`worker-0...2`):
   ```bash
   cat ansible/inventory_all.ini
   ```
2. **Connect via SSH:** SSH into the `loadbalancer` VM using the SSH key generated by Terraform:
   ```bash
   ssh -i secrets/private_key.pem ubuntu@<LOADBALANCER_IP_ADDRESS>
   ```

---

## 1. Install HAProxy

- **What this step does:** Updates APT package repositories and installs the `haproxy` package from the standard Ubuntu software archives.
- **Why we are doing it:** HAProxy is a high-performance TCP/HTTP load balancer. In this cluster, it serves as the stable external ingress entry point for web application traffic entering from OpenStack routers, distributing requests evenly across the Kubernetes worker nodes.

```bash
sudo apt-get update
sudo apt-get install -y haproxy
```

---

## 2. Configure HAProxy (`/etc/haproxy/haproxy.cfg`)

- **What this step does:** Backs up the default HAProxy configuration and creates a custom `/etc/haproxy/haproxy.cfg` file that binds an HTTP frontend on port `80` (`http_front`) and forwards traffic to a backend (`http_back`) composed of all 3 worker nodes on port `30080` using round-robin load balancing and TCP health checks.
- **Why we are doing it:** 
  - `bind *:80`: Listens for standard web traffic arriving at the load balancer.
  - `balance roundrobin`: Distributes incoming HTTP requests sequentially across `worker-0`, `worker-1`, and `worker-2` so no single worker is overwhelmed.
  - `server worker-X ... check`: The `check` parameter instructs HAProxy to continuously probe port `30080` on each worker node. If a worker node crashes or goes offline, HAProxy automatically removes it from rotation so users don't experience downtime.
  - `30080`: By workshop convention, our Kubernetes Gateway API / Cilium Ingress controller is exposed across all worker nodes via a static NodePort at `30080`.

Before creating the config file, gather the **private IP addresses** of your 3 worker nodes (`worker-0`, `worker-1`, `worker-2`). You can find these in your Terraform output (`cd initInfra && terraform output`) or OpenStack dashboard.

```bash
# 1. Back up the default HAProxy configuration
sudo cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg.bak

# 2. Write the custom configuration (replace 10.0.X.X with your actual worker IPs)
cat <<EOF | sudo tee /etc/haproxy/haproxy.cfg
global
    log /dev/log local0
    log /dev/log local1 notice
    chroot /var/lib/haproxy
    stats socket /run/haproxy/admin.sock mode 660 level admin expose-fd listeners
    stats timeout 30s
    user haproxy
    group haproxy
    daemon

defaults
    log     global
    mode    http
    option  httplog
    option  dontlognull
    timeout connect 5000
    timeout client  50000
    timeout server  50000

frontend http_front
    bind *:80
    default_backend http_back

backend http_back
    balance roundrobin
    # Replace the IPs below with your actual worker node internal IP addresses:
    server worker-0 10.0.10.11:30080 check
    server worker-1 10.0.10.12:30080 check
    server worker-2 10.0.10.13:30080 check
EOF
```

## 3. Configure OpenStack Floating IP Policy Routing (Netplan)

- **What this step does:** Creates a persistent Linux Netplan routing policy (`/etc/netplan/60-policy-routing.yaml`) that assigns an explicit routing table (`table: 102`) for any traffic originating from the Load Balancer's primary interface IP (`enp4s0`), directing it through the OpenStack subnet gateway (`10.0.50.1`).
- **Why we are doing it:** When OpenStack assigns a Floating IP (FIP) to a VM with multiple network interfaces or specific DHCP routing tables, return packets can sometimes leave via the wrong interface or gateway (asymmetric routing), causing external connection timeouts. Policy routing guarantees that reply packets for external requests arriving via the Floating IP are routed back out through the correct OpenStack router gateway.

```bash
# 1. Determine the primary IP address of enp4s0
LB_IP=$(ip -4 addr show enp4s0 | grep -oP '(?<=inet\s)\d+(\.\d+){3}')
echo "Load Balancer IP on enp4s0 is: ${LB_IP}"

# 2. Create the Netplan policy routing configuration
cat <<EOF | sudo tee /etc/netplan/60-policy-routing.yaml
network:
  version: 2
  ethernets:
    enp4s0:
      routing-policy:
        - from: ${LB_IP}
          table: 102
      routes:
        - to: default
          via: 10.0.50.1
          table: 102
EOF

# 3. Apply the Netplan rules immediately
sudo netplan apply
```

> [!WARNING]
> If your OpenStack subnet uses a different default gateway IP than `10.0.50.1` (check with `ip route show default`), replace `via: 10.0.50.1` with your actual gateway IP.

---

## 4. Restart and Enable HAProxy

- **What this step does:** Validates the syntax of `/etc/haproxy/haproxy.cfg`, restarts the HAProxy systemd service, and enables it to start automatically on boot.
- **Why we are doing it:** Syntax checking (`haproxy -c`) prevents accidental typos from crashing the service. Restarting and enabling HAProxy applies the new round-robin backend configuration and ensures load balancing survives VM reboots.

```bash
# 1. Validate HAProxy configuration syntax
sudo haproxy -c -f /etc/haproxy/haproxy.cfg

# 2. Restart and enable HAProxy
sudo systemctl restart haproxy
sudo systemctl enable haproxy

# 3. Check service status
systemctl status haproxy --no-pager
```

## ✅ Verification Check

- **What this check does:** Verifies that HAProxy configuration syntax is valid and tests that a process is actively listening on TCP port 80.
- **Why we are doing it:** Confirming port 80 is listening ensures the front-end load balancer is ready to accept HTTP traffic once the worker nodes and Gateway API are deployed.

```bash
# 1. Validate HAProxy configuration
sudo haproxy -c -f /etc/haproxy/haproxy.cfg

# 2. Verify port 80 is open and listening
sudo ss -tulpn | grep :80
```
